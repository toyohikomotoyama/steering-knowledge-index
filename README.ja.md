# Steering + Knowledge Index：AIエージェントに「昨日」を思い出させる

[English](README.md)

AIエージェントは、かなり賢くなった。

コードを読み、仕様を理解し、不具合を調べ、実装し、テストする。

でも、長く一緒に仕事をすると一つ問題が出てくる。

**昨日を忘れる。**

最終的に正しかった仕様は `docs/` に残せる。

けれど、そこへ至るまでに、

- 何を疑ったか
- どの仮説が外れたか
- 何を見落としたか
- どこで作業が止まったか
- 誰の回答を待ったか
- 調査の横で何が見つかったか

といった経験は、きれいな仕様書から消えていく。

そして次に似た問題が起きたとき、AIはまた最初から考え始める。

このリポジトリは、その問題から生まれた三層のプロジェクト記憶モデルを提案する。

## 三つの層

```text
docs/
    Current Truth
    "What is true now?"

.steering/
    Current Work State
    + Chronological Experience
    "What happened, where are we now, and how did we get here?"

.knowledge-index/
    Retrieval Paths into Experience
    "Where are the relevant memories?"
```

`docs/` は、現在の正しい仕様・確認済みの挙動・制約を置く場所。

`.steering/` は、調査や実装を進めながら、仮説、失敗、訂正、回答待ち、実装、検証、残作業を時系列で残す場所。

`.knowledge-index/` は、過去の経験を要約して保存する場所ではない。現在の問いから、関係するSteeringへ戻るための索引である。

読む順番は単純だ。

> **Current Truth first. Experience when needed.**

まず `docs/` を読む。

現在の仕様だけで答えられるなら、そこで終わる。

「なぜこうなったのか」「前にも似たことがあったか」「前回どこで詰まったか」のように経験が必要になったときだけ、`.knowledge-index/` から `.steering/` へ降りる。

## Steeringは完成報告ではない

Steeringは、答えが出た後に綺麗に書き直す報告書ではない。

調査を始めた時点で作り、作業中に更新する。

```text
仮説A
  ↓
調べる
  ↓
外れた
  ↓
別の設定を発見
  ↓
実環境と辻褄が合わない
  ↓
追加確認
  ↓
別の構成要素が見つかる
  ↓
理解を訂正
```

こう進んだなら、この順番を残す。

結果を知った後で「最初から正解を知っていた」物語にしない。

なぜなら、未来のAIに役立つのは正解だけではなく、**どこで間違え、何をきっかけに方向を変えたか**だからだ。

一方、TODOや現在のステータスは最新状態へ更新してよい。

**TODOの履歴を残すのではなく、TODOが動いた理由を残す。**

だからSteeringは作業中には進行管理面になり、完了後にはそのまま経験記録になる。

昨日までの進捗表が、今日からの歴史資料になる。

そしてその歴史資料が、次の作業では危険予知の材料になる。

## 一つの経験に、一つの名前を強制しない

調査は予定通りには進まない。

文字コードを調べ始めたら、サーバ構成の不一致や古いdocsが見つかるかもしれない。

最初から「これは文字コードConceptの記録」と分類すると、途中で見つかった別の経験を落としやすい。

そのためSteeringは、Conceptではなく**一連の作業・調査・出来事**を単位にする。

後からKnowledge Index側で、同じSteeringへ複数の入口を作る。

```text
文字コード ──────┐
サーバ構成 ──────┼→ 同じSteering
環境との差異 ────┘
```

分類体系も最初から決めない。

まず `misc.md` のような受け皿から始め、実際の経験が蓄積して自然なまとまりが見えてきたときに分ける。

## なぜ要約ではなく「原記録への入口」なのか

同じ過去でも、現在の問いによって意味は変わる。

「なぜこの仕様なのか」と聞く場合と、「今回も同じところで詰まりそうか」と聞く場合では、同じSteeringの読み方が違う。

だからKnowledge Indexには固定した物語を保存しない。

**経験は保存する。意味は現在の文脈で再構築する。**

そして再構築が怪しければ、原典へ戻って確認できる。

> **Stored experience is not the same thing as present cognition.**

## リポジトリそのものを引継ぎ資料にする

一般的な引継ぎ資料は、作成者が「未来の人が何を聞くか」を予想して整理する。

しかし未来の疑問を全部予想することはできない。

三層モデルでは、後任者や新しいAIエージェントが現在の問いから逆向きにたどれる。

```text
現在の問い
  ↓
docs/ で現在状態を確認
  ↓
理由・履歴・類似経験が必要
  ↓
.knowledge-index/
  ↓
関連する .steering/
  ↓
当時の経験を現在の文脈で読み直す
```

つまり日常の開発そのものが、少しずつ**逆引き可能な引継ぎ資料**を作っていく。

## 似た構造はある。しかし、そこから設計したわけではない

このモデルを実務で育てた後、いくつか既存の考え方との構造的な類似に気づいた。

Event Sourcingに似て、Steeringは出来事の履歴を残し、Docsは現在状態に近い。ただしSteeringからDocsを機械的に再生するわけではない。仮説、誤り、会話、外部確認などを人間やAIが検証し、現在の正を更新する。

さらに、仏教の唯識思想にも「蓄積された経験」と「現在の認識」を分けるという構造上の類似が見える。これも設計の出発点ではなく、実務上の問題を解いていった後に気づいたものだ。

そして、変化し続けるものを現在の形だけで固定しない、という意味では、方丈記の「ゆく河の流れは絶えずして、しかももとの水にあらず」という感覚も連想させる。

これらは技術的な同一視ではない。

**実務上の問題を解くために運用を育てた結果、既存の複数の考え方と似た構造へ収斂した**、という位置づけである。

## Steeringという名前

この名前に合わせて思想を作ったわけではない。

もともとは別のエンジニアが使っていた「Steering file」という呼び方を採用しただけだった。

しかし運用を育てていくと、不思議なくらい名前が合ってきた。

> **Steeringは「舵取り」である。今日の航海を記録し、その記憶を明日の航海の舵取りに使う。**

現在のKnowledgeだけを残すと、何が失われるのか。

AIエージェントに必要なのは、Knowledgeだけなのか。

もしかすると必要なのは、**経験を思い出せること**なのかもしれない。
